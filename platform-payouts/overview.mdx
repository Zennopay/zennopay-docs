title: "Platform Payouts"
description: "Send asynchronous bank payouts from a prefunded balance with one server-to-server API."
---

Platform Payouts lets a platform send a bank payout from its prefunded
Zennopay balance. The API validates the beneficiary, applies configured
controls, reserves funds atomically, and durably queues execution. External
rail calls happen in a background worker after the API transaction commits.

<Info>
  A `202 Accepted` response means the payout is durable and processing. It is
  not proof that the beneficiary received funds. Poll or consume webhooks until
  the payout becomes `completed`, `failed`, or `reversed`.
</Info>

## Core properties

- **Server-to-server only.** Requests use the same HMAC signing scheme as the
  Partner API. Never expose the credential to a browser or app.
- **Int64-safe money.** Every monetary field is a base-10 signed-int64 string.
  VND values are whole dong—never decimals.
- **Durable asynchronous execution.** Acceptance and the execution outbox are
  committed together. Network calls do not run inside the HTTP transaction.
- **Tenant and environment isolation.** Balances, beneficiaries, payouts, and
  routes are bound to the authenticated tenant and test/live mode.
- **Stable idempotency.** Retrying the same request with the same key returns
  the original payout. Reusing a key for different input fails.

## Lifecycle

```text
created -> processing -> completed | failed
                            completed -> reversed
```

| Status | Meaning |
|---|---|
| `created` | Accepted and held for review. |
| `processing` | Queued, submitting, externally pending, or recovering an ambiguous outcome. |
| `completed` | Delivery was reported successful. |
| `failed` | The payout will not complete. |
| `reversed` | A previously completed payout was later reversed. |

Internal queue and recovery states are intentionally collapsed into
`processing`.

## Availability

Destination and currency availability is enabled per account and environment.
Do not infer Platform Payouts coverage from QR Payments coverage. A destination
is usable only when beneficiary creation and a payout readiness test succeed in
the intended environment.

## Live prerequisites

Before live traffic, Zennopay must provision live credentials, source-network
allowlisting, a prefund balance in each settlement currency, destination
routes, compliance and risk controls, beneficiary protection keys, and a
signed HTTPS webhook endpoint. Missing dependencies fail closed. Sandbox
success does not itself enable live mode.
